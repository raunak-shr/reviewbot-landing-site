Technical architecture
Companion sheet

One process.
One queue.
One graph.

The design doc says what ReviewBot does. This sheet says how it is built, and the drawings say most of it. A single Python container sits behind a GitHub App, work is handed off through a Postgres-backed queue, and a LangGraph pipeline of four agent nodes does the reviewing.

Every durable byte lives in Postgres. The container holds nothing: kill it mid-run and the job comes back with its attempt count intact.

Section 1 — At a glance
Sheet 1 of 5

Three responsibilities, one container.

Receive events, run the review graph, maintain the code index. They share a process but never a code path, and nothing between them is held in memory.

Fig. 1 — Service routing one pull request, end to end

Read it left to right and the whole service is one sentence: something happens, it becomes a queued job, the job runs a graph, and the graph's verdict is written down before it is announced. The dashed lines are not flow: they are the one thing every box shares. There is no developer API anywhere on this drawing, and no second worker fleet; at ten pull requests a month a second process would be idle infrastructure with an operational cost.

Never inline

The receiver answers GitHub inside a second and reviews nothing on that thread. X-GitHub-Delivery is the idempotency key, so a redelivery is a no-op.

Safe to kill

On SIGTERM the receiver returns 503 so GitHub retries, in-flight jobs get 60 seconds, and anything unfinished goes back to the queue with its attempt count preserved.

One replica, deliberately

Serial index ordering, debounce state and at-most-one-run-per-scope are held by advisory locks, so a second replica is safe. The default is still one.

Section 2 — The review pipeline
Sheet 2 of 5

Two branches, and a model decides neither.

The graph has exactly two conditional edges. Both are keyed on state the service already holds: the run type, and the repository's stack. Never on what an agent returned.

Fig. 2 — LangGraph wiring nodes, edges, and where the branches are

Triage is the only node that batches. Bug & Security and both Practices agents make one call per file; Triage receives findings and never code, so an entire five-file fast-path scope is about 1,500 tokens and fits in a single call. That is also why Triage can see a bug finding and a practice finding on the same function together, and merge them.

The whole file, not the hunk.

Diffs decide scope — which files to look at, and whether the change was meaningful at all. But an agent judging correctness gets the entire file, because a bug is very often the interaction between the three lines that changed and the thirty that did not.

Context Builder adds up to three related files per call: depth-1 graph dependents first, then depth-2, then semantic matches above a 0.80 cosine threshold. Truncation drops whole units, lowest priority first, never a file cut mid-function, which produces exactly the ragged context the node exists to prevent.

Degrade, don't fail.

A parse failure gives that file no AST expansion; it is still reviewed as raw content and a parse_failure metric fires with the language. An unavailable index empties related_context and marks the run degraded_context = true.

The run continues in both cases. A review that saw less is worth more than a review that did not happen, provided the record says which one you got.

Section 3 — Entry points
Sheet 3 of 5

Five ways work starts. No timer runs a full scan.

Everything else the service does is a consequence of one of these five. The two expensive run types, baseline and monthly, have no scheduler path at all.

Fig. 3 — What starts a run, and what stops one the filter order is cheapest first

The dashed path is the one that matters operationally. The scheduler and the operator CLI enqueue without passing any of the webhook filters, because there is no hostile payload to defend against. The CLI pays a different different toll: scan-monthly refuses a repository whose full_scan_enabled is false, prints the modelled cost before it enqueues, and records who started it.

Section 4 — The data layer
Sheet 4 of 5

A finding has to survive the commit that moved it.

Line numbers change on every rebase. If a finding's identity were its location, every push would raise it again as new, and a developer who dismissed it once would have to dismiss it forever.

Fig. 4 — Finding identity and the code index what makes two findings the same finding

The fingerprint is why ack and dismiss are worth anything. It is a hash of the repository, the file path, the enclosing symbol and the normalised rule: four things that survive a rebase, so a decision recorded against it keeps applying across every later push. Without it, "dismiss" would mean "until the next commit", and the five-dismissal rule would be measuring noise.

Traversal depth

Two hops, by a recursive CTE on symbol_edges. Past about three hops on a dense graph the latency stops being acceptable, and that, not throughput, is the first thing that forces a real re-architecture.

Idempotency

A mid-run kill costs duplicated LLM spend and never a duplicated comment. Every job is keyed, and the router writes rows before it posts anything.

Drift repair

The monthly command carries a reconciliation pass that detects and repairs index drift. reviewbot reconcile runs the same repair with no LLM spend at all.

Section 5 — The envelope
Sheet 5 of 5

Six gates stand between an event and a paid call.

Every one of them is a decision not to spend. They are ordered so the cheapest test runs first, and the most expensive thing the system can do needs a human to type a flag.

Fig. 5 — What stops a call from being made cost controls, in the order they apply

The ordering is the design. Debounce collapses a burst of four pushes into one run before anything is read; the hash gate discards unchanged files before anything is sent; and the fast path simply does not run the Practices agents, which is why a pull request costs what it costs. A full-codebase scan is roughly two orders of magnitude more expensive than a fast-path run, which is why it is the one operation a person has to ask for by name.

The compute story holds to roughly ten times the current volume. The first genuine re-architecture is triggered by traversal depth or repository count, not by how many pull requests arrive.

ReviewBot

Scheduled multi-agent code review, running as a GitHub App against the Northwind frontend and backend repositories. It reads the diff, holds the merge on a major finding, and releases it on a named developer's signature.

Every value on this sheet — the sizing, the thresholds, the tuning constants and the scaling limits — is taken from the technical architecture document as written, and is a specification rather than a measurement. Nothing here has been benchmarked yet; the day-60 review is what turns the modelled numbers into observed ones.
